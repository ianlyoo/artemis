# 설계

[English](design.md) · 한국어

이 문서는 Artemis가 어떻게 짜여 있고 왜 그런지 설명합니다. 각 절의 끝에는 그 생각이 `src/artemis/`의 어디에 있는지 적었습니다.

## 문제

에이전트 하나가 세션 하나에서 일하면 따라가기 쉽습니다. 한 일을 읽고 확인하면 됩니다. 문제는 한 사람이 에이전트 여럿을 동시에 부릴 때 시작됩니다.

**사람이 병목이 됩니다.** 에이전트가 모든 행동 전에 물으면, 사람은 판단할 수도 없는 것을 하루 종일 승인하다가 결국 읽지 않고 승인하게 됩니다. 아무것도 묻지 않으면 위험한 행동이 보이지 않는 곳에서 일어납니다. 어느 쪽이든 한 사람이 돌릴 수 있는 에이전트 수를 정하는 것은 기계가 아니라 그 사람의 주의력입니다.

**맥락을 잃습니다.** 세션마다 자기 일만 봅니다. 한 대화에서 내린 결정은 다음 대화에 없고, 전체 그림이 남는 곳은 사람의 머릿속뿐이라 무슨 일이 있었는지 기억하려고 로그를 다시 읽게 됩니다.

**"끝났다"가 끝났다는 뜻이 아니게 됩니다.** 일을 한 에이전트가 끝났다고 말하는 에이전트이기도 합니다. 보고는 확인이 아니고, 몇 번 지나면 어느 결과가 검사됐고 어느 결과가 말로만 설명됐는지 아무도 구분하지 못합니다.

**변경이 여러 길로 들어옵니다.** 어떤 에이전트는 main에 바로 커밋하고, 어떤 에이전트는 브랜치를 남기고, 어떤 에이전트는 파일을 그 자리에서 고칩니다. 무엇이 반영됐는지, 어떤 검사를 통과했는지, 무엇이 깨뜨렸는지 아무도 말하지 못합니다.

Artemis는 지시를 더 늘리는 대신, 각 문제에 구조 장치 하나로 답합니다. 대화하는 리드 하나, 각자 워크트리에서 동시에 도는 작업자, 일과 분리된 판정자, 배포 레인 하나, 사람을 기다리는 결정의 짧은 목록, 그리고 다른 모든 것이 그 위의 조회인 장부 하나입니다.

## 주의력 예산

Artemis가 내세우는 것은 사람의 주의력이고, 그래서 그것을 셉니다. 한 번 물음은 사람의 결정함에 들어간 결정 하나입니다. 끝난 작업은 배포 레인을 거쳐 대상 브랜치에 닿은 작업 하나입니다. 상태 줄과 다이제스트는 언제나 두 수를 함께 보여 줍니다. 예: `3 tasks done · asked you 1×`.

사람에게 가는 행동은 세 종류뿐입니다:

- **돈이 나가는 일**: 결제, 구매, 유료 요금제
- **되돌릴 수 없는 삭제**: 복구할 수 없는 모든 것
- **당신 이름으로 보내는 일**: 그 사람 이름의 게시, 글, 이메일, 푸시

선은 되돌릴 수 없음과 누군가의 이름으로 행동함에 그었습니다. 시스템이 스스로 고칠 수 없는 실수가 바로 그것이기 때문입니다. 그 아래에서 묻는 것은 주의력을 쓰게 하고, 읽지 않고 승인하는 습관을 가르치며, 그것은 묻지 않는 것보다 나쁩니다. 프로젝트는 `artemis.toml`에서 목록을 줄일 수 있지만, 이 셋 밖으로 늘릴 수는 없습니다.

결정은 일이 그 지점에 닿았을 때 하나씩 카드로 옵니다. 무엇을, 왜 그 사람이어야 하는지, 무엇을 근거로 하는지, 아무것도 하지 않으면 어떻게 되는지가 적혀 있습니다. 마지막 물음의 답은 언제나 "아무 일도 일어나지 않음"입니다. 결정 하나를 붙잡아 두어도 나머지 일은 멈추지 않습니다.

그 밖의 일은 모두 리드 몫입니다. 반려된 결과, 실패한 검사, 병합 충돌, 비정상 종료, 권한 거부는 다이제스트에 `stuck`으로 나오고, 리드가 다시 시키거나 접습니다. 사람에게 가는 질문이 되지 않습니다.

코드에서는: `src/artemis/roles.py`가 세 종류를 `Interrupt`로 정의합니다. `src/artemis/config.py`는 `artemis.toml`의 `[interrupts]`에서 프로젝트의 목록을 읽고 세 종류 밖의 것은 거부합니다. `src/artemis/attention.py`가 장부 이벤트에서 두 수를 셉니다.

## 리드

사람은 에이전트 하나와 이야기합니다. 리드는 사람의 말을 작업으로 바꾸고, 시작하고, 지켜보고, 무엇이 바뀌었는지 알려 줍니다.

Claude Code에서 리드는 그 사람의 대화형 세션 그 자체입니다. `artemis start`가 Artemis 지침을 시스템 프롬프트에 덧붙여 엽니다. 리드는 사람의 말을 말한 그대로 기록하고, 동시에 돌 수 있는 작업으로 나누고, 작업마다 검사를 붙여 시작합니다. 그다음 `artemis wait`를 백그라운드로 돌립니다. 이것은 알릴 만한 일이 생기면 돌아옵니다: 작업이 반영됐거나 막혔을 때, 결정을 물었거나 답을 받았을 때. 리드는 그것을 한두 줄로 전하고 다시 기다립니다. 프롬프트 아래의 상태 줄은 아무도 묻지 않아도 수를 보여 줍니다.

리드는 자기 질문을 스스로 승인하지 못하게 막혀 있습니다. 리드 세션은 에이전트에게 `artemis approve`, `artemis decline`, `artemis resume`을 막는 설정으로 시작합니다. 이것은 보안 경계가 아니라 규칙입니다. 리드도 같은 사용자로 돌기 때문에 원리상 다른 길로 장부를 쓸 수 있고, 그래서 Artemis는 사람만 승인할 수 있다고 주장하지 않습니다. 이 명령은 사람이 직접 실행합니다(Claude Code에서 `! artemis approve 1`은 에이전트 권한 밖에서, 사람으로서 명령을 실행합니다). 승인이 나면 리드가 행동을 실행하고 한 일을 기록합니다.

데모는 규칙 기반 계획기를 가진 내장 대화 리드를 써서, 계정 없이 흐름 전체를 해 볼 수 있습니다. 이 리드는 말하는 모든 줄에 `mock`을 붙입니다.

코드에서는: `src/artemis/lead.py`가 리드 세션을 열고(`start_cli`, `session_settings`) 대화 리드와 그 계획기(`plan`, `chat`)를 가집니다. `src/artemis/templates/lead.md`가 리드의 지침입니다. `artemis wait`와 `artemis statusline`은 `src/artemis/attention.py`에 있습니다.

## 동시에 일하는 작업자

작업마다 자기 Git 워크트리와 자기 브랜치(`artemis/task-N`)에서 돌기 때문에, 작업자는 사람의 작업 폴더도 서로의 파일도 건드리지 않습니다. 동시에 `max_workers`개까지 돌고, 나머지는 줄을 섰다가 앞의 것이 끝나면 시작합니다.

분리된 감독 프로세스가 사람 없이 작업 하나를 끝까지 돌립니다. 작업자에게 표준 입력으로 작업을 주고, 기다리고, 작업자가 출력한 것을 결과가 아니라 주장으로 다룹니다. 그다음 작업자가 아니라 감독이 바뀐 것을 커밋합니다. 작업자는 고치기만 합니다. Git의 공유 파일에 쓸 권한이 필요 없고, 충돌 표시를 남기거나 아무것도 바꾸지 않은 작업자는 판정 전에 걸러집니다.

판정자가 반려하거나, 병합 결과에서 검사가 실패하거나, 대상 브랜치가 움직여 충돌이 나면, 감독은 이유를 붙여 다시 시킵니다. 작업마다 세 번까지입니다. 충돌이면 감독이 지금의 대상을 작업 브랜치에 병합하고 작업자에게 해결을 맡깁니다. 마지막 시도 뒤에도 안 되면 작업은 `stuck`이 되어 리드에게 갑니다.

헤드리스 작업자는 사람의 권한으로 돌기 때문에 울타리를 칩니다. Claude Code 작업자는 자기 워크트리에서 읽고 고치고, Git을 보고, 작업의 검사를 돌릴 수 있습니다. 그 밖의 것은 아무에게도 묻지 않고 거부됩니다. 승인할 사람이 그 자리에 없기 때문입니다. Codex 작업자는 셸을 끈 채로 돌고, 파일과 검사에는 Artemis가 그 워크트리에 띄운 작은 도구 서버로만 닿습니다. OpenCode 작업자는 읽기, 수정, 작업의 검사만 허용하고 나머지는 거부하는 권한 프로필 아래에서 돕니다. API 작업자는 아무것도 실행할 수 없습니다. 추적 중인 파일을 요청 한 번에 보내고, 답에 담긴 경로를 Artemis가 모두 확인한 뒤에 씁니다.

코드에서는: `src/artemis/supervise.py`(`dispatch`, `supervise`, 재시도 루프, `_commit`, `_merge_target`). `src/artemis/agents.py`는 에이전트 목록과 작업자 명령을 만들며, Claude Code 허용 목록도 여기서 만듭니다. `src/artemis/worker_adapters.py`는 Codex와 OpenCode 설정을 가지고 각자의 마지막 메시지를 주장으로 읽습니다. `src/artemis/codex_tools.py`는 Codex 도구 서버, `src/artemis/api_worker.py`는 API 작업자입니다. `src/artemis/mock_worker.py`는 데모와 CI가 쓰는, AI 없는 작업자입니다.

## 유일한 상태인 장부

장부는 프로젝트 안의 SQLite 파일 하나, `.artemis/ledger.db`입니다. Artemis가 아는 모든 것이 여기에 있습니다: 사람이 쓴 그대로의 요청, 작업과 기준, 실행, 제출, 증거, 판정, 결정, 배포 영수증.

두 종류의 기록이 있습니다. **테이블**은 지금의 상태를 담습니다. **이벤트**는 덧붙이기만 하는 기록입니다. 상태가 바뀔 때마다 테이블 변경과 같은 트랜잭션에서 이벤트가 쓰이고, 데이터베이스 트리거가 이벤트의 수정과 삭제를 거부합니다.

사람이 보는 모든 것은 그 행들 위의 **조회**입니다: 상태 줄, 결정함, 다이제스트, `artemis show`. 어느 것도 자기 상태를 따로 갖지 않습니다. 그래서 세션은 버려도 됩니다. 리드를 닫았다 열어도, 감독이 죽어도, 다음에 읽는 쪽은 같은 사실을 봅니다.

코드에서는: `src/artemis/ledger.py`가 테이블, 이벤트, 트리거, 그리고 작업마다 지금 상태 하나를 주는 `work` 뷰를 가집니다. 전이마다 쓰기 트랜잭션 하나를 열고, 사람의 멈춤을 확인하고, 변경을 이벤트와 함께 저장합니다.

## 증거와 판정자

일을 한 에이전트가 끝났는지 정하지 않습니다. 판정자가 정하고, 판정자는 기록된 것으로만 판정합니다.

작업마다 기준이 있습니다. 명령 기준은 작업자 커밋의 깨끗한 체크아웃에서 그 명령이 0으로 끝나면(기대하는 글이 정해져 있다면 그것을 출력하면) 충족됩니다. 파일 기준은 커밋에 그 파일이 있으면 충족되고, 그 다이제스트가 기록됩니다. 이 증거는 감독이 직접 잡습니다. 작업자의 주장은 남지만 무게가 없습니다. 검사는 작업자가 쓴 코드를 돌리기 때문에, 사람 셸의 환경 변수 전부가 아니라 허용 목록(PATH, HOME, 로캘, 임시 폴더, 툴체인 변수, 그리고 `[ship] pass_env`에 적은 것)만 받습니다. 판정은 셋 중 하나입니다: 통과, 충족되지 않은 기준 목록과 함께 반려, 판정할 수 없을 때(예: 기준이 없는 작업) 정지.

사람이 읽는 모든 줄은 그것을 어떻게 아는지 말합니다:

| 라벨 | 뜻 |
|---|---|
| `shipped` | 합친 결과에서 검사가 통과한 뒤 대상 브랜치에 반영됨 |
| `verified` | 판정자가 증거를 통과시킴; 아직 반영 전 |
| `reported` | 작업자가 그렇다고 말함; 아직 아무것도 확인 안 됨 |
| `inferred` | 리드 자신의 판단 |
| `decided` | 사람이 결정한 것 |
| `running` | 지금 작업자가 하는 중 |
| `stuck` | 리드가 처리 중 |

코드에서는: `src/artemis/judge.py`가 증거 기록, 기준, 규칙 기반 판정자를 정의합니다. 판정자는 기록된 증거만 읽고 매번 같은 판정을 냅니다. 라벨은 `src/artemis/attention.py`가 `work` 뷰에서 계산합니다.

## 배포 레인

작업이 대상 브랜치에 닿는 길은 하나입니다.

1. 판정을 받은 커밋을 고정해서 받습니다. 검사한 것이 정확히 반영될 것입니다.
2. 사람의 멈춤을 확인합니다. 멈춤이 있으면 아무것도 돌지 않습니다.
3. 버리는 워크트리에서 커밋을 지금의 대상 위에 병합합니다.
4. 그 병합 결과에서 프로젝트의 검사를 돌립니다.
5. **통과:** 3단계 이후 대상이 움직이지 않았을 때만 대상을 검사한 커밋으로 옮기고, 커밋, 대상, 검사마다 명령, 종료 코드, 출력 다이제스트를 담은 영수증을 저장합니다.
6. **실패나 충돌:** 대상은 그대로 두고 이유를 그 작업의 감독에게 돌려보냅니다.

반영은 한 번에 하나씩입니다. 프로젝트마다 잠금이 하나라 두 작업이 같은 브랜치를 옮기려고 다투지 않습니다. 대상이 사람의 작업 폴더에 체크아웃된 브랜치라면, 로컬 수정이 방해하지 않을 때만 빨리 감기합니다. 아니면 브랜치 참조를 비교 후 교체로 옮깁니다. Artemis는 푸시하지 않습니다. 브랜치를 공개하는 것은 `send as you` 종류의 결정입니다.

대상은 기본이 `main`이고, `artemis.toml`의 `[ship] target`에서 정합니다. `.artemis/` 아래 파일을 추적하는 커밋은 거부됩니다.

코드에서는: `src/artemis/ship.py`(`ship`, `_merge`, `_advance`, `lane`). `src/artemis/ledger.py`는 최신 판정이 바로 그 커밋을 통과시킨 경우에만 검사나 영수증을 기록합니다.

## 결정함과 멈춤

결정은 리드가 만듭니다(`artemis ask`). 종류, 무엇을, 왜 사람이어야 하는지가 붙습니다. 사람이 승인하거나 거절할 때까지 결정함에서 기다립니다. 카드에는 그 요청의 작업들이 지금까지 한 일도 적혀 있어, 사람은 증거를 앞에 두고 결정합니다. 승인 하나는 그 행동을 한 번 허락합니다.

**멈춤**은 반대 방향으로 작동합니다. `artemis stop`은 장부에 멈춤을 씁니다. 감독, 재시도, 배포 레인은 단계마다 멈춤을 확인하고, 멈춤이 있는 동안 아무것도 하지 않습니다. 새 일도 시작할 수 없습니다. 멈춤에는 만료도 자동 해제도 없습니다. 사람만 `artemis resume`으로 풀 수 있고, 리드 세션은 이 명령을 실행할 수 없습니다.

코드에서는: 결정과 멈춤은 `src/artemis/ledger.py`의 전이입니다. 카드와 결정함은 `src/artemis/attention.py`가 그리고, `src/artemis/cli.py`가 `approve`, `decline`, `stop`, `resume`을 엽니다.

## 다이제스트

다이제스트는 사람이 따라잡는 방법입니다. 마지막으로 읽은 뒤 바뀐 것을 다룹니다. 머리 줄 하나에 기간, 수, 막힌 것이 있는지를 쓰고, 그 아래에 손댄 작업마다, 내린 결정마다 한 줄씩, 라벨로 시작해 씁니다.

```text
Last 9 min · 3 tasks done · asked you 1× · nothing stuck
shipped   #1 Add a --json flag            main 2d1c61c · python3 -m unittest exit 0
shipped   #2 Add a --done filter          main 02446a5 · python3 -m unittest exit 0
shipped   #3 Document both in the README  main dd72f65 · README mentions --json, --done
decided   D1 Post a release note to the team  you approved · posted to the demo outbox
```

읽으면 그 기간이 읽음으로 표시되고, 다음 다이제스트는 거기서 시작합니다. 기간은 시각이 아니라 상대 시간("Last 9 min")으로 씁니다. 작업 줄은 증거를 검사의 이름으로 밝혀서, 사람은 아무것도 열지 않고 무엇이 검사됐는지 봅니다.

코드에서는: `src/artemis/attention.py`(`digest`, `window`, `counts`, `status`, `statusline`).

## 실패를 다루는 법

무언가 실패하면 고치는 곳은 실패가 나온 곳입니다. 에이전트를 다룰 때의 반사 작용은 문제가 보인 자리에 가드를 더하는 것입니다: 재시도, 대기, 특수한 경우, 프롬프트의 한 줄. 가드 하나하나는 한동안 통하지만, 모이면 아무도 따져 볼 수 없는 시스템이 됩니다. Artemis는 설계의 무엇이 그 실패를 낳았는지 묻고 그것을 바꿉니다. 예를 들어 한때는 작업자가 자기 변경을 직접 커밋했는데, 어떤 에이전트의 샌드박스는 Git 공유 파일에 쓸 수 없었습니다. 고친 방법은 권한 예외가 아니었습니다. 이제 커밋은 감독이 하고, 작업자는 고치기만 합니다.

실패는 삼키지 않고 기록합니다. 실패한 검사는 출력 다이제스트와 함께 행으로 남고, 막힌 작업은 이유를 달고 있으며, 다이제스트가 둘 다 보여 줍니다.

코드에서는: 실패한 전이는 이벤트와 함께 되돌려집니다(`src/artemis/ledger.py`). 실패한 검사와 충돌은 기록되어 되돌려 보내집니다(`src/artemis/ship.py`, `src/artemis/supervise.py`). 프로세스가 죽은 감독은 다음에 누군가 장부를 읽을 때 막힘으로 표시됩니다(`src/artemis/attention.py`의 `reap`).

## 일부러 뺀 것

Artemis는 더 큰 개인 시스템에서 시작했습니다. 이 저장소는 그 공개판이고, 몇 부분은 일부러 뺐습니다.

- **푸시와 배포.** 배포 레인은 로컬 브랜치에서 멈춥니다. 푸시는 사람이 정합니다.
- **다른 리드.** 리드는 Claude Code(와 데모의 대화 리드)만 맡습니다. 리드에게는 승인을 사람에게 남겨 둘 방법이 필요하기 때문입니다. Codex, OpenCode, API 작업자는 작업만 맡습니다.
- **Windows 작업자.** 단위 테스트는 Windows에서도 돌지만, Windows의 실제 작업자는 아직 지원하지 않습니다.
- **실제 데이터.** 코드, 테스트, 데모의 모든 요청, 작업, 이름은 지어낸 것입니다.
